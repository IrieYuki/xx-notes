# 学习笔记的编写与维护（速查笔记 / 刷题笔记）

> 正本仓库：https://github.com/IrieYuki/xx-notes
> 本地安装路径：`~/.hermes/skills/note-taking/study-reference-notes/`（两边内容保持一致）

任务类别：用户要求新增或修改**自己的中文学习笔记**（「Python XX 速查笔记」「LeetCode 刷题笔记」等）。这类笔记的用途是「忘记时速查」，所以**结构一致 + 示例真的能跑**比篇幅重要。

## 1. 先定位文件

笔记都在用户的 git 仓库里（2026-09 起；旧路径 `~/python/note/`、`~/leetcode-notes/` 已废弃，不要再往里写）：

- 速查笔记（Python / Numpy / Pandas / Matplotlib / Seaborn / C / C++ / MySQL 共 8 份）：
  **正本在 `~/xx/xx-notes/notes/`**（远端 `IrieYuki/xx-notes`，技能也在同仓 `verified-cheatsheet-notes/`；`notes/` 同时是 Obsidian 库）；
  `~/My_Python_Study/note/*.md` 只剩指向正本的**链接桩**（几百字节），别再往桩里写内容。
  （`IrieYuki/My-Python-Study` 这个 GitHub 仓库 2026-10 已按用户要求删除；`~/My_Python_Study` 只是本地目录，没有远端，别往它推送。）
  改动一律在正本仓库做，改完提交推送并核对远端 blob sha。
- LeetCode 刷题笔记：`~/My_LeetCode_Study/leetcode-notes/`，文件名两位序号前缀（`00-复杂度分析.md`、`01-刷题路线图.md`）；题解代码放 `~/My_LeetCode_Study/solutions/`
- 附件里给的 `note/xxx.md`、`leetcode-notes/xxx.md` 是相对路径：先 `ls` 对应目录定位；开宽泛文件搜索前先限定到具体子目录。
- 用户会搬/改目录：动手前 `ls` 一次确认路径真实存在；写文件报 `FileNotFoundError` 时先怀疑路径已经改了，而不是权限问题。**仓库改名 / 目录改名时要一次性搜全引用**：仓库内 README、`~/My_Python_Study/note/*.md` 的链接桩、已安装技能（`~/.hermes/skills/note-taking/`）里的路径与正本 URL、`verified-cheatsheet-notes/SKILL.md` 的示例命令，改完两个仓库都要 push 并核对远端。
- 先全文读一遍再动手；后续替换要基于真实文件内容，不要凭对话里贴过的片段。

## 2. 速查笔记的固定结构（用户认可的定稿形态，新内容照此写）

**索引在最前 + 条目格式统一**。用户读这份文件的方式是「按索引跳转查一条用法」，所以能跳转、条目长得一样、示例真能跑，比篇幅和 DRY 重要。

整体骨架：

````
# 标题
## 怎么用这份文件            ← 使用说明 + 格式约定 + 章节顺序（3~5 条）
## 索引 · 速查表             ← 原来的「目录」和「末尾速查表」合并成一张表，放在正文之前
## 第一部分　内置函数（直接写名字调用）
### A1　类型转换 → A2 数学与数值 → A3 聚合与判断 → A4 序列生成与迭代 → A5 排序与筛选
### A6 类型与属性 → A7 类与装饰器 → A8 字符串表示与编码 → A9 输入输出与格式化 → A10 动态执行与反射
## 第二部分　各类型常用方法（点号调用）
### B1 list → B2 str → B3 dict → B4 set → B5 tuple      ← 按日常使用频率排
## 学习建议
````

- 索引表：三列 `| 分类 | 用法（点击跳转） | 一句话作用 |`，**一行一个函数/方法**（不要为了紧凑把同类合并成一行），用法列链接到该条目标题，分类列写 `B1 list 列表` 这种「编号 + 名字」（全角空格换成半角，否则撑列）。
- 条目：一条一个 `###`（旧稿用 `####`；全部从 JSONL 渲染，渲染器统一输出 `## <分类>` + `### 条目`），
  标题是「`名字` 一句话作用」，固定顺序（v2：解析 ｜ 操作 ｜ 提醒）：

````
### `名字(参数)` 一句话作用

**解析**　干什么（一句话白话）

| 参数 | 默认值 | 作用 |
|------|--------|------|
| x | 必填 | …逐项解释每个参数/选项 |

返回：返回什么

**操作**

```python
...可直接运行的示例，`#` 后写真实输出，会报错的写法注释掉并标 ❌（Linux 命令示例下面跟 ```text 真实结果块）
```

> ⚠️ 要点或坑（原「备注」合并进这里；没有就整行不写）
````

  标题里的「一句话作用」**禁止空格包标点**（` → `、` / `、` ↔ `、`命令 -x`、`--help`）：GitHub 会把空格算成 `-`、
  Obsidian 的 gfm-heading-links 插件会把连续空白/连字符压成一个 `-`，两边锚点不一致 → Obsidian 里死链。
  渲染器对每个标题断言双端 slug 相等，不相等直接报错（改法：箭头贴字写、`min()、max()` 用顿号、命令选项并进正文参数表）。

  解析（干什么 + 参数表 + 返回）**永远都在**，没内容写「—」，用户就是靠它回答「怎么调用 / 得到什么 / 什么时候炸」。标题里的名字必须唯一（方法名前带接收者 `l.` `s.` `d.` `t.`；互为反操作的成对函数合并写 `chr(i)、ord(c)`），因为索引行直接镜像标题。
- 内容**允许跨板块重复**：`in` 在 list / str / set 各写一遍、`pop` 在 list / dict / set 各写一遍。用户从索引直接跳进来，重复比交叉引用好用，**不要为了 DRY 删掉**。
- 面向初学者（用户在学 Python 基础语法）：核心价值是机制与坑（方法返回 `None`、`remove` vs `discard`、浅拷贝共享嵌套层、`[[0]*2]*2` 行共享、`property` 当方法调会炸），写清「为什么」并给 ❌/✅ 对照；别写大段理论。
- 版本相关特性标版本（dict 保序 ≥3.7、`popitem` LIFO ≥3.7、`|` 合并字典 ≥3.9、`{x=}` ≥3.8）。
- 记录 schema、锚点算法、渲染契约见 `references/entry-schema-and-index.md`；现有章节与缺口见 `references/python-quickref-inventory.md`。
- **大改一律走「JSONL 数据 → 渲染器」**（不要手写正文）：渲染器同时产出索引表、正文与锚点，格式才不会漂；
  具体命令、非 Python 笔记（C / C++ / SQL）的约定见 `references/multi-language-notes.md`。

## 3. 两种改法

### A. 小改：往既有分类里加条目

1. 先 `grep -n '^#\{2,4\} ' <笔记.md>` 拿真实标题，确认加到哪个分类、插在哪条前后。
2. **同一次编辑里同步两处**：正文条目 + 索引表该分类的行（顺序与正文一致）。若新增分类或改了顺序，还要同步开头「怎么用这份文件」里的顺序说明。
3. 替换用 `execute_code` + 纯 `open(path, encoding="utf-8").read()/write()`：每处替换前 `assert text.count(old) == 1`，全部改完**一次写回**。逐处手改会漏改或重复插入。
4. 收尾核对：`text.count("```")` 为偶数、索引行数 == `#### ` 条目数、每条索引链接都能在条目标题算出的锚点集合里找到（跑 §4 的脚本）。

### B. 大改（重排 / 统一格式 / 全文重写）：数据驱动重建

1. **先备份**原文件：`shutil.copy2(note, note + ".bak-旧版")`。改版是破坏性的，用户会先审格式再让你落盘。
2. 把每条内容写成**结构化记录**，分多次 `execute_code` 追加到 `~/.hermes/cache/scratch/entries.jsonl`，一个 cell 写 10~20 条；最后一个 cell 统一渲染。分块是为了超时不丢进度（单 cell 超 300s 会被杀且 kernel 状态清空）。
3. 渲染时**程序化生成索引链接**：slug = 条目标题的 GitHub 锚点算法结果，并 `assert` slug 全唯一。链接目标与渲染器自动生成的标题锚点同名，换渲染器也不会跳空。
4. **先出预览、拿到格式确认再动原文件**：渲染结果写到 `_预览-<笔记名>.md` 交用户看；确认后再覆盖原文件，并删掉预览文件（用户要求文件夹干净）。
5. 记录 schema、slug 算法、渲染步骤见 `references/entry-schema-and-index.md`；示例校验直接跑 `scripts/verify_notes_examples.py`。

## 4. 必做：把示例真跑一遍

「注释里的输出」就是这类笔记的价值，必须验证，不能凭记忆写。

- 把新章节每条示例抽成断言脚本放进 `execute_code`：`chk(label, got, want)` 收集通过/失败，最后一次 print 汇总。
- **自动比对注释与真实输出**（省事且覆盖全）：`python3 scripts/verify_notes_examples.py <笔记.md>` —— 逐条 exec 代码块 + tokenize 提注释 + AST 求值，把 `#` 里的字面量和真实结果比。手写断言覆盖「声明式的坑」，脚本覆盖「示例里的输出」，两者都跑、分开报数。
- 断言覆盖**注释声称的输出**和**异常类型**：`t[0]=9` → TypeError、`{[1,2]}` → TypeError、`s.remove(不存在)` → KeyError、`s.discard(不存在)` 不报错、空集合 `pop()` → KeyError、`d["k"]` → KeyError、`d.get(k, 默认值)` 的返回值、遍历中增删 dict → RuntimeError。
- 随机 / 无序行为不断言具体值：`set.pop()` 只断言「返回元素 ∈ 集合」。
- 报告里给出「实测 N 项断言通过 / 0 失败」和本机 Python 版本；笔记里给版本相关特性标版本（dict 保序 ≥3.7、`popitem` LIFO ≥3.7、`|` 合并字典 ≥3.9）。

### 非 Python 笔记（C / C++ / SQL）怎么验

校验脚本按语言选，全部用**技能正本的绝对路径**调（见 references/multi-language-notes.md）：
`scripts/verify_notes_examples.py`（Python）/ `verify_c_blocks.py --lang c|cpp` / `verify_sql_blocks.py`。

- **C / C++：编译 + 运行**。每个代码块都要是**完整可编译程序**（含 `#include` 与 `main`），小白才复制得走；
  交互示例在代码顶部写一行 `// 输入：Tom 18` 声明该块的 stdin（生成器与校验器共用这条规则），
  生成器把真实 stdout 写回尾部 `// 运行结果：…`。
- **示例里不要打印地址 / 时间 / 随机数**：每次运行都不一样，根本没法校验（改成打印「相等吗：1」这类布尔结果）。
  `%p`、`std::chrono`、`rand()` 都属此列。
- **本机没有数据库服务时（如 MySQL）**：把可移植子集在 SQLite 上真跑，专有语法
  （AUTO_INCREMENT / SHOW / DESCRIBE / DATE_FORMAT / TRUNCATE / GRANT…）在结果处标「未实跑」并让校验器跳过 ——
  **绝不编造结果**。生成器与校验器里的 SCHEMA / SEED 必须逐字一致，否则校验会假报不一致；
  两个解释器各跑一遍（它们带的 SQLite 版本不同，会遮住 SQL 翻译函数的 bug）。
- **条目多（>40）时可以把某门语言/库的撰写外包给子代理**，但它的汇报（「55/55 通过」）**不算证据**：
  自己在工作区用技能正本的渲染器重渲染、重跑校验器，并把所有 `warn`（⚠️）行集中读一遍 ——
  断言密度最高、最容易写错的就是那里（审阅时抓到过自相矛盾的表述）。子代理只产出 JSONL + 预览 md，不碰 git。
- 汇报时主动说清**哪些没验到**：本机没有的服务/库、被排除在可校验范围外的示例、「跳过 N 条」都不等于「全部通过」。

## 5. 坑

- **别把带行号的读取结果当正文回写**：`read_file` 的输出每行带 `序号|` 前缀，用它做 read-modify-write 会往文件里灌行号和竖线（代码示例里的 `|` 也会被截断）。脚本里一律 `open()` 读原文。
- **Markdown 表格里的竖线要转义**：单元格内表示「或」运算写 `` `\|` ``，否则表格列错位。
- **别只加用户点名的那一项**：用户说「加 list 的增删函数」，往往接着就要 tuple / set / dict / str。一次补齐同族容器（或先问一句要不要一起补），并在结尾列出仍然缺哪些章节。
- 插入内容时不要顺手重排或精简原有示例；但用户明确要求「重排 / 统一格式」时就整份重建（见 §3-B），不要半套上去。
- **校验脚本跑示例前先给 `input()` 喂 stdin**（`sys.stdin = io.StringIO("Tom\n18\n1 2 3\n")`），否则它会真的等键盘、把 cell 卡到 300s 被杀；每条语句执行前重喂一次，只喂一次会让 `int(input())` 拿到上一句的内容、报出假失败。
- 自动比对只适用**顶层简单语句**：`for`/`def`/`class` 内部的行、prose 注释（「输出 20」「按长度排」）、`❌` 行要跳过；注释里的解释性括号先剥掉再当字面量解析（「10（二进制字符串）」→ `10`）。
- **每条示例的代码块要自包含**（用到 `Person`/`Circle` 就在本块里定义）：逐条独立执行时，依赖上一条的块会 NameError，而这正是校验要抓的问题。
- **写生成脚本时的引号**：payload 以引号结尾紧贴三引号结束符（`'None'` 后面接 `'''`）会 SyntaxError —— 代码块字符串一律「首尾各留一个换行、再 `.strip("\n")`」；也**别拿反引号当 Python 字符串定界符**（` 在 markdown 里到处都是）。
- **「删除旧文件」这类措辞先核实再动手**：全文重写是**就地覆盖同一个路径**，仓库/目录里不会另外留一份旧文件（本地备份 `.bak-旧版` 也要先 `ls` 确认在不在）。先 `git ls-files` + `ls` 查清，确实没有就直说没有，别凭空造一次删除动作。
- **生成器按 `(分类, 名字)` 去重**：改完某条已有条目的文字后，必须**重建 JSONL**
  （删掉 `xxx_entries.jsonl`，再按 1→N 顺序重跑各批次脚本），否则那条会被当成重复**静默跳过**、旧文字留在笔记里。
  生成器遇到编译/运行/执行失败的条目要直接报错退出 —— 跑不通的示例永远不能进笔记。
- **渲染 / 校验脚本只认正本那一份**：一律调技能目录的绝对路径
  （`~/.hermes/skills/note-taking/verified-cheatsheet-notes/scripts/...`）。工作区里留的旧副本会**静默**产出不同结果
  （实例：旧 renderer 不认 `lang`/`out`，渲染出的 SQL 笔记没有结果块，校验器把整份笔记当成「全部跳过」而看着像通过了）。

## 6. 汇报格式

不贴全文。给：改了哪些章节（小表格）、同步了目录 / 索引 / 顺序说明；验证结果（断言数、注释比对一致性、链接数与失效数、围栏配对、本机 Python 版本）；结尾附 `MEDIA:/绝对路径` 让用户在客户端直接打开笔记；再一句话说明还缺哪些章节可选做。
- 重排类改动额外说明：新结构骨架、条目数、旧版备份路径（`<文件>.bak-旧版`）、预览文件是否已删。
- 用户把笔记放在 git 仓库里，改完常接着让你提交推送：提交前先 `git status` / `git ls-files` 看真实跟踪路径，推送后用 blob sha 两边对照 + `gh api` 读回确认，别只说「推好了」。
