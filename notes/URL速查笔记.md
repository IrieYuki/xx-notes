## 一 基础结构

### `URL 的组成` 协议+主机+端口+路径+参数+锚点

**解析**　URL 就是「网址」，是浏览器告诉服务器「我要哪个东西」的完整地址。它由 6 部分组成：协议（scheme，怎么传）、主机（host，找哪台机器）、端口（port，找哪个服务）、路径（path，要哪个资源）、查询字符串（query，附带参数）、锚点（fragment，页面内定位）。整条读法是 `协议://主机:端口/路径?查询#锚点`，其中只有协议和主机是必须的，其余都能省略。

**操作**

```text
http://shop.example.com:8080/product/list?id=42&sort=price#reviews
└─┬─┘  └──────┬──────┘ └┬┘ └────┬──────┘ └────┬──────┘ └──┬──┘
协议         主机       端口    路径          查询          锚点
```

> ⚠️ 坑：端口省略时用协议默认值（http 是 80，https 是 443）。写 `http://a.com:80/` 和 `http://a.com/` 请求到的是同一处。

### `scheme 协议` 用什么协议说话 http 还是 https

**解析**　scheme 是 URL 最前面那个词，决定用哪套规则传数据。最常遇到 `http`（明文，路上能被中间人看到）和 `https`（加密，多了一层 TLS）。此外还有 `ftp`、`file`、`javascript`、`data` 等。做渗透时碰到 http 站点，抓包就能直接看到内容；https 就得想别的办法。

**操作**

```text
http://example.com       → 明文传输，端口默认 80
https://example.com      → 加密传输，端口默认 443
file:///etc/passwd       → 直接读本机文件
javascript:alert(1)      → 执行一段 JS（XSS 里常见）
```

> ⚠️ 坑：`https` 只保证「传输过程」加密，不代表网站本身安全；它和有没有漏洞是两回事。

### `host 与 port` 找哪台机器哪个房间

**解析**　host（主机）是你要访问的服务器，可以写域名（`example.com`，靠 DNS 翻译成 IP），也可以直接写 IP。port（端口）决定连服务器上的哪个服务，像房间号：80 一般是网站、22 是 SSH、3306 是数据库，各住各的。

**操作**

```text
http://example.com/path         → 域名，端口用默认的 80
http://93.184.216.34/path       → 直接写 IP
http://127.0.0.1:8080/path      → 本机的 8080 端口（打自己靶场常用）
http://example.com:2375/        → 非默认端口要显式写，这里是 2375
```

> ⚠️ 坑：`127.0.0.1` 和 `localhost` 都指本机。有些服务只监听 127.0.0.1（只对本机开放），外网连不上、只有本机能访问——这类服务在渗透里是重点目标。

### `path 路径` 资源在服务器上的位置

**解析**　path 是主机后面那一段，指明你要服务器上的哪个资源，长得像文件路径 `/admin/login.php`。它以第一个 `/` 开始，遇到 `?` 或 `#` 结束。path 不一定对应真实磁盘文件，但服务器常把它映射到磁盘文件——这正是「路径穿越」的由来。

**操作**

```text
http://example.com/index.html          → 站点根目录下的文件
http://example.com/admin/login.php     → 多级目录
http://example.com/api/user/42         → REST 风格，42 是用户编号
http://example.com/images/             → 以 / 结尾通常是目录
```

> ⚠️ 坑：末尾有没有 `/` 可能返回完全不同的内容（`/admin` 可能 301 重定向，`/admin/` 才是真页面），换目录时把斜杠补上再试。

### `query 查询字符串` 问号后面就是给服务器的参数

**解析**　query（查询字符串）从 `?` 开始，格式是 `名=值`，多个用 `&` 连起来。它是给服务器「传数据」的地方：搜索关键词、商品编号、页码、排序方式都放这里。做渗透时，这是最常被篡改的地方。

**操作**

```text
http://example.com/search?q=python&page=2
                            └──┬──┘  └──┬──┘
                          名=值        多个参数用 & 连接

?id=42            → 一个参数
?q=a&sort=desc    → 两个参数
```

> ⚠️ 坑：`?` 全条 URL 里只有一个，从第二个参数起一律用 `&` 连接；写成 `?a=1?b=2` 是错的。

### `fragment 锚点` 井号之后页面内定位浏览器自己用

**解析**　fragment（片段标识）从 `#` 开始，指向页面内的某个位置（比如 `#reviews` 跳到评论区）。关键点：**它只给浏览器自己用，根本不会发给服务器**。所以服务器永远看不到 `#` 后面的东西，把参数写在 `#` 后面等于没写。

**操作**

```text
http://example.com/doc#chapter-3      → 打开页面后直接滚到第三章
https://example.com/app#/user/42      → 单页应用（SPA）常把路由塞在 # 后面
```

> ⚠️ 坑：抓包时看不到 `#` 后的内容——这不是抓包工具的问题，是协议就这么定的。

## 二 字符编码

### `百分号编码` 特殊字符为什么要写成 %XX

**解析**　URL 只能安全地携带一小部分字符（字母、数字、`-_.~`）。空格、中文、`#`、`&` 要么是保留字符、要么根本不是 ASCII，直接放进去会歧义或被拒。解决办法叫「百分号编码」（URL 编码）：把一个字节写成 `%` 加两位十六进制。比如空格是 `%20`；中文「中」的 UTF-8 是三个字节 `E4 B8 AD`，编码后就是 `%E4%B8%AD`。

**操作**

```text
原始：  "hello world & 中"
编码后： hello%20world%20%26%20%E4%B8%AD

在 Python 里验证：
>>> from urllib.parse import quote
>>> quote("hello world & 中")
'hello%20world%20%26%20%E4%B8%AD'
```

> ⚠️ 坑：十六进制大小写都合法，`%2f` 和 `%2F` 等价。不同工具输出的大小写可能不同（curl 偏小写，Python 偏大写），别以为小写就错了。

### `常用编码对照表` 背下这 7 个就够入门

**解析**　渗透测试里翻来覆去就是这几个字符的编码，背熟了一眼就能看懂别人写的 payload。下表左边是原始字符，右边是它在 URL 里的百分号编码（这里统一用大写形式，小写等价）。

**操作**

```text
字符     编码    为什么要编
空格     %20    URL 里的空白（表单里也常写成 +）
'        %27    单引号，SQL 注入 payload 常用
#        %23    不编码就会被当成锚点的开头
&        %26    不编码就会被当成参数分隔符
=        %3D    不编码就会被当成「名=值」的分隔
/        %2F    不编码就变成了路径分隔
%        %25    百分号自身，编码出来就是 %25
```

> ⚠️ 坑：`%` 要最先想到——想传一个真实的 `%20` 字面量，得写成 `%2520`（先把 `%` 编成 `%25`，后面的 `20` 原样保留）。

### `保留字符 vs 非保留字符` 哪些必须编码哪些不用

**解析**　URL 字符分两类。**非保留字符**（unreserved）：字母、数字、`-`、`_`、`.`、`~`，它们没有任何特殊含义，可以原样出现。**保留字符**（reserved）有特殊用途：`:/?#[]@` 负责切分 URL 结构，`!$&'()*+,;=` 有子分隔含义。想在一个「值」里原样表示保留字符，就必须百分号编码。

**操作**

```text
非保留（不用编码）： A-Z a-z 0-9 - _ . ~
保留 · 结构类：      : / ? # [ ] @
保留 · 子分隔类：    ! $ & ' ( ) * + , ; =
```

> ⚠️ 坑：编码「多余」不报错（`%41` 就是 `A`），但编码「太少」会让 URL 结构被误解，服务器解析出的参数就和你以为的不一样——很多绕过技巧正是利用这一点。

## 三 请求与地址

### `查询字符串 key=value&` 多个参数怎么拼

**解析**　一个参数是 `名=值`，多个参数用 `&` 串起来，整体跟在 `?` 后面。服务器读取时先按 `&` 切成一段段，每段再按第一个 `=` 切成名和值。所以「值」里如果本身含 `&` 或 `=`，必须编码（`%26`、`%3D`），否则会被切开。

**操作**

```text
?name=tom&age=18&city=beijing
 └──┬───┘ └─┬───┘ └────┬─────┘
  参数1     参数2      参数3

同一个名出现两次：?id=1&id=2  → 取第一个还是最后一个，看后端实现
```

> ⚠️ 坑：`#` 之后的内容不发给服务器，所以参数千万别写在 `#` 后面。

### `GET vs POST` 两种请求方式怎么选

**解析**　这是两种 HTTP 请求方法。**GET**：参数放在 URL 的查询字符串里，用来「取」数据（打开网页、搜索）。**POST**：参数放在请求体（body）里，用来「提交」数据（登录、发帖），URL 里通常看不到。GET 的 URL 会被记进浏览器历史、服务器访问日志；POST 的数据藏在 body 里，相对不显眼，但抓包一样看得到。

**操作**

```text
GET /search?q=python HTTP/1.1     ← 参数写在 URL 里
Host: example.com

POST /login HTTP/1.1              ← 参数写在 body 里
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=tom&password=123456
```

> ⚠️ 坑：GET 对 URL 长度有限制，POST 基本没有；但「POST 更安全」是误解——没上 https，两者抓包都一览无余。

### `相对 URL vs 绝对 URL` 地址写全还是写半截

**解析**　**绝对 URL** 写全：`https://example.com/a/b.html`。**相对 URL** 只写一部分，相对「当前页面」来解析：`b.html`（同目录）、`../img/x.png`（上一级目录）、`/login`（网站根目录）、`//cdn.com/x.js`（协议相同、只换主机）。浏览器会自动把相对地址拼成绝对地址再发请求。

**操作**

```text
当前页面：https://example.com/shop/list.html

b.html             →  https://example.com/shop/b.html      （同目录）
../user/tom.html   →  https://example.com/user/tom.html    （上一级）
/cart              →  https://example.com/cart             （从根目录）
//static.com/a.js  →  https://static.com/a.js              （协议相同、主机不同）
```

> ⚠️ 坑：`../`（上一级）是路径穿越的基础；`//` 开头省略协议，很容易骗过只看 http/https 的过滤。

## 四 命令行 curl

### `curl 里怎么写 URL` 在命令行发一次请求

**解析**　curl 是最常用的命令行 HTTP 工具，能把你从「只会点浏览器」升级到「用脚本精确发请求」。基本写法是 `curl [选项] "URL"`，默认把服务器返回的内容打印到屏幕。做渗透时用它精确控制请求头、参数、请求方法。

**操作**

```text
curl "http://127.0.0.1:8080/"                          # 直接 GET，打印网页
curl -i "http://127.0.0.1:8080/"                       # -i 连响应头一起打印
curl -I "http://127.0.0.1:8080/"                       # -I 只取响应头（HEAD 请求）
curl -X POST -d "a=1&b=2" "http://127.0.0.1:8080/"     # 发 POST 表单
curl -v "http://127.0.0.1:8080/"                       # -v 打印请求/响应全过程，调试用
```

> ⚠️ 坑：URL 里带 `&` 时必须用引号把整条包起来，否则 shell 会把 `&` 当成「放后台执行」：`curl http://x/?a=1&b=2` 会被 shell 拆成两条命令。

### `curl 自动编码参数` 让 curl 帮你转义 GET 参数

**解析**　手写 `%20`、`%26` 很容易错。curl 的 `-G`（把数据拼到 URL 查询串里）加 `--data-urlencode`（自动做 URL 编码）能替你搞定：你说人话，它出编码。二者配合时 curl 会把数据拼成 `?名=值` 的查询串。

**操作**

```text
$ curl -s -o /dev/null -v -G --data-urlencode "q=hello world" http://127.0.0.1:8765/search
> GET /search?q=hello+world HTTP/1.1

$ curl -s -o /dev/null -v -G --data-urlencode "q=a#b&c=d" http://127.0.0.1:8765/search
> GET /search?q=a%23b%26c%3dd HTTP/1.1     ← # & = 全被编码，不会破坏结构
```

> ⚠️ 坑：`--data-urlencode` 把空格编成 `+`（这是表单编码），而标准的百分号编码是 `%20`；两者服务器通常都认，但和你别处写的 `%20` 不一样，别对不上就慌。

### `井号与注释` 在 URL 和 shell 里都是特殊符号

**解析**　`#` 在两个地方都很特别。在 **URL** 里，它是 fragment 的起点，`#` 后面的内容**不发给服务器**。在 **shell**（你敲命令的地方）里，`#` 是注释的起点，`#` 后面的内容**不会被命令执行**。两处都会「把后面的东西吞掉」，所以写命令行时最容易被它坑。

**操作**

```text
URL 里：   curl "http://x/page#section"   → 服务器只收到 GET /page
shell 里： echo hi      # 这一行从 # 起是注释，不执行
           curl "http://x/?a=1"
```

> ⚠️ 坑：shell 只把「词的开头」的 `#` 当注释（所以 `a#b` 里的 `#` 不是注释），但 URL 里 `#` 永远是 fragment；两套规则叠在同一行命令上，最容易出错。

## 五 安全视角

### `URL 在安全里的用途` 注入点参数篡改 CSRF🔒

**解析**　🔒 URL 是 Web 渗透的「主战场」：每一个参数（`?id=`、`?url=`、`?file=`）都是潜在的**注入点**，你改它的值、看返回变化，就能判断后端怎么处理。常见玩法：**参数篡改**（把 `id=42` 改成 `id=43`，看能不能看到别人的订单，这叫越权 / IDOR）、**参数注入**（把 `?url=/profile` 改成 `?url=http://evil.com`，让服务器去请求外网，造成 SSRF 或开放重定向）、**CSRF**（构造一个受害者会「自动发起」的请求 URL，借他已登录的身份干坏事，比如 `<img src="https://bank.com/transfer?to=me&amount=9999">`，用户一打开被挂图的页面钱就转了）。

**操作**

```text
?id=42              → 改成 ?id=43，试试能不能看到别人的数据（越权 / IDOR）
?url=/profile       → 改成 ?url=http://evil.com，看服务器会不会去请求外网（SSRF）
?file=1.pdf         → 详见「路径穿越」那条

<img src="https://bank.com/transfer?to=me&amount=9999">   ← 典型 GET 型 CSRF
```

> ⚠️ 坑：只对**有授权**的目标（自己的靶场、CTF 平台、明确授权的项目）动手；改别人的参数、发 CSRF 请求都是违法的。

### `路径穿越` 往上跳目录读不该读的文件🔒

**解析**　🔒 如果服务器拿 URL 里的参数去拼文件路径、又不做检查，就能用 `../`（上一级目录）一路往上跳，读到网站根目录之外的文件，比如 `../../../../etc/passwd`。这叫**路径穿越**（Path Traversal）。常见的可疑参数名：`file`、`path`、`page`、`download`、`template`、`include`。

**操作**

```text
?file=report.pdf                        → 正常读一份报告
?file=../../../../etc/passwd            → 往上跳，试着读系统文件
?file=....//....//etc/passwd             → 过滤只删一次 ../ 时的绕过写法
?file=..%2f..%2f..%2fetc%2fpasswd        → 把 / 编码成 %2F 绕过过滤

用 curl 测时要加 --path-as-is：
$ curl -s -o /dev/null -v --path-as-is "http://127.0.0.1:8765/static/../secret.txt"
> GET /static/../secret.txt HTTP/1.1
（不加 --path-as-is，curl 会自己把 ../ 吃掉，变成 GET /secret.txt）
```

> ⚠️ 坑：curl 默认会自动把 `../` 规范化掉，直接测会「看起来没效果」；做路径穿越测试一定要加 `--path-as-is`。

### `%00 空字节截断` 用空字节骗过后缀检查🔒

**解析**　🔒 `%00` 是一个空字节（NULL）。历史上有些语言（如老版本 PHP）底层用 C 风格字符串，遇到空字节就认为「字符串到此结束」。于是 `shell.php%00.jpg` 在检查扩展名时看到的是 `.jpg`（合法），真正用文件名时却在 `%00` 处被截断成 `shell.php`——白名单就被绕过了。今天主流环境已修复，但它仍是经典的绕过思路，值得知道。

**操作**

```text
?file=shell.php%00.jpg     → 检查时看到 .jpg，落地时被截成 shell.php
?file=../../etc/passwd%00  → 让 %00 截掉后面多余的校验字符
```

> ⚠️ 坑：现代 PHP（5.3.4+）、Java、Python 等已不受影响；这条现在更多是用来理解「当年为什么能绕」，别在已修复的环境上浪费时间。
